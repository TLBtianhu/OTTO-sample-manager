## 1. 先量：`--mem-probe`（真实 HWND，不 show）

新探针走**和正常启动完全相同**的初始化路径（`main.zig` 在几个点调 `mark`），窗口是
真实 `HWND`（380×700），但 `app.flags.hidden = true`：不 show、不抢焦点、不进任务栏。
字体、D3D、缩略图都走真实路径：

* 字体：`newWindow` 里 `SetWindowPos` 触发的 WM_SIZE → `surface.frame()`（真实
  `fontdb.scan` + 字形栅格化）；
* 上屏：向窗口发 WM_PAINT → `surface.paint`（D3D11 设备 + 翻转交换链，或 GDI）；
* 缩略图：真的滚动列表（`ctx.applyScroll` + `frame` + WM_PAINT），让 `row_thumb`
  穿过 L2 缓存与 `ui.image` 的图像图集，而不是只调 `thumb.get` 拿字节；
* 空闲：抽 `PeekMessage` 10 秒，`otto-lite` 自己的 150 ms tick 照常跑。

每个时刻记四类数：

| 列 | 来源 | 说明 |
| --- | --- | --- |
| `ws_mib` | `K32GetProcessMemoryInfo` | 判据（宪章「常驻内存」） |
| `private_mib` | 同上 `PrivateUsage` | 私有提交（任务管理器的「提交大小」一侧） |
| `image/mapped/private_pages` | `K32QueryWorkingSet` + `VirtualQuery` | 驻留页按类型分账：DLL 代码 / 映射文件 / 我们自己的分配 |
| 分项列 | 各层自己的账 | L2 缩略图、图像图集、解码保留、字形图集、已加载字体、画布、线程数、模块 WS |

一条命令（`zig/mem.ps1`）会建一份**测得到的库**：2000 行循环指向 100 个真实图片副本
（`%TEMP%\otto-mem-probe\files`），所以每一屏滚过去都有真缩略图可画；然后跑两遍
（隔离 on / off）并打印汇总。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File zig\mem.ps1            # debug
powershell -NoProfile -ExecutionPolicy Bypass -File zig\mem.ps1 -Release   # release
powershell -NoProfile -ExecutionPolicy Bypass -File zig\mem.ps1 -NoBuild -Idle 10
```

> 探针自己的代码与 import（模块枚举 + GDI DIB 自检）在稳定状态下**不额外占内存**：
> 同一构建连续 6 次（隔离开）读到 42.58–42.63，去掉这两个诊断是 42.59。
> 例外：**刚构建完**的第一轮读到过 45.61，多出来的 3 MiB 全在 `otto-lite.exe` 的
> 代码页（模块表里 3.01 vs 1.18 MiB）——系统（AV/DWM）正在读这个新 exe 的瞬态。
> 下表取稳定值，并把这个 45.61 当上界记在这里。

## 3. 钱花在哪：映像页逐个模块 + 私人页逐项

**映像页 17.70 MiB 是别人的代码**（隔离开，空闲时，前 10）：

```text

mem-probe: module ntdll.dll                        ws_mib=1.86
mem-probe: module combase.dll                      ws_mib=1.28
mem-probe: module otto-lite.exe                    ws_mib=1.18   ← 我们自己的全部代码页

mem-probe: module DWrite.dll                       ws_mib=0.97
mem-probe: module MSCTF.dll                        ws_mib=0.87

mem-probe: module CoreMessaging.dll                ws_mib=0.76
mem-probe: module CoreUIComponents.dll             ws_mib=0.69

**私人页 23.47 MiB**（空闲）：L2 缩略图 3.52 + 库 4.78 + 画布 1.01 + 字形图集 1.25 +

**D3D11 的价钱**（`--d3d`，同一个探针、同一时刻，两次运行 72.59 / 72.68）：

mem-probe: stage=idle  ws_mib=72.68  image_mib=36.56  private_pages_mib=34.08  threads=48

D3D 设备 + 交换链一次要 **+30.0 MiB**（72.63 − 42.63）：映像 +18.6（36.34 vs 17.70）、
私人 +10.7、线程 8 → 48（驱动自己的池），present p50 也从 **0.05 ms** 涨到
**4.17 ms**（同一帧、同一份画布，见 §4 第 5 项）。

## 4. 做了哪几项（每项单独量，debug 链）

改动前 128.64 MiB（debug，隔离开，空闲）。每一步只改一件事、重新跑一次探针：

| # | 改动 | 落在哪 | 空闲 WS | Δ |
| ---: | --- | --- | ---: | ---: |
| 0 | 起点 | — | 128.64 | — |
| 1 | 图像图集按需增长（512² 起，满了翻倍到 2048²） | `nanoui/ui/images.zig` | 113.70 | **−14.94** |
| 2 | DirectWrite 借我们的字体字节，不再整份拷贝 | `nanoui/ui/dwrite.zig` | 94.03 | **−19.67** |
| 3 | 字体文件只读映射（`readFileAlloc` → `MapViewOfFile`） | 新 `nanoui/ui/tt/fontmap.zig`、`tt/fontdb.zig` | 74.81 | **−19.22** |
| 4 | 工作线程栈 16 MiB → 1 MiB（band 线程 512 KiB） | `thumbs.zig`、`preview_panel.zig`、`ports/watch.zig`、`nanoui/ui/raster.zig` | 74.68 | −0.13 WS / **−46.08 提交** |
| 5 | 上屏默认 GDI（`--d3d` 保留旧路径） | `nanoui/windows/{app,surface}.zig`、`app/options.zig`、`app/main.zig` | 45.59 | **−29.09** |

每项的来龙去脉：

1. **图像图集**：`images.zig` 的 `size` 是编译期常量 2048，第一张图就 `alloc(2048²×4)`
   = **16.00 MiB** —— 列表里 32 点缩略图只要 64²。改成 `side` 从 `min_size`（512²，
   1 MiB）起步，单张图放不下才翻倍（上限 2048²，大预览图才用得到），并把「图集搬家」
   接到已有的 `reset_during_frame` 重绘机制上。实测 16.00 → 1.00 MiB。
   连带修 `opengl.zig`（按 `pictures.size` 重建纹理）与 `metal.zig`（`syncImages`
   记住纹理边长，图集长大就重建）。
2. **DirectWrite 的字体副本**：`CreateInMemoryFontFileReference` 的 owner 传 null 时
   DirectWrite 会**把整份字体拷进自己的堆**——`msyh.ttc` 19.7 MB 于是被算了两遍。
   传一个只有 `AddRef/Release` 的 `IUnknown`（`dwrite.zig` 的 `font_owner`）就变成
   借用；生命周期是安全的：`TextSystem.deinit` 先放图集（连带所有 face）再放字体库。
   实测正好省 19.67 MiB（就是那一个文件）。
3. **字体文件的页**：`readFileAlloc` 把 19.7 MB 读进私有页；改成只读映射后，只有
   真正读到的页才算驻留。实测 `mapped` 只涨 0.5 MiB，私有页掉 19.2 MiB —— 一个
   窗口用 82 个字形只需要字体文件的很小一部分。非 Windows 平台没有映射，回退到读文件。
   顺带：`fontdb.scan` 的复用缓冲只有 64 KiB（`max_end=37102353` 是某个 name 表的
   **偏移**，不是缓冲大小——上一轮差点按 37 MB 去改，这里纠正）。
4. **线程栈**：`std.Thread` 的默认 `stack_size` 是 **16 MiB**，每个工作线程都是按这个
   提交的。watcher / 取图 / 预览各 1 MiB，绘制 band 线程 512 KiB（每帧都起，原来每帧
   都提交 16 MiB）。WS 几乎不动（栈的未用页本来就不驻留），但**私有提交 −46.08 MiB**：
   127.19 → 81.11。
5. **上屏**：这是最后也是最大的一刀。`--gdi` 实测（同一帧重复 present 20 次）：
   GDI p50 0.22 ms / D3D p50 4.16 ms，而 D3D 还要多 27 MiB 常驻。DWM 本来就会合成
   GDI 窗口，所以撕裂风险不变；代价是没有 vsync、窗口尺寸变化时没有翻转模型那么顺。
   因此 `otto-lite` 默认走 GDI，`--d3d` 一行切回旧行为（`nanoui.Options.gdi` 默认仍是
   false，别的 app 不受影响）。

**没做／按数据不做的**：

* **L2 缩略图预算**（默认 32 MiB）：100 张 96×96 只有 3.52 MiB，不是大头；宪章把
  L2 排除在 50 MiB 之外，所以不动。风险记在这里：长距离滚动理论上能吃到 32 MiB。
* **字形图集**：核实为已经按需（首帧 82 个精灵 = 82 次栅格），512²（1.25 MiB）没长过。
* **交换链缓冲数/尺寸**：切成 GDI 之后不存在了；`--d3d` 下 2 个缓冲各 1.01 MiB，
  不是大头。
* **分配器归还 OS**：没有改（`init.gpa` 的保留页是 §3 里那 ~11 MiB 的一部分）。
  要动它得先把它拆开，本轮没做。
* **D3D 驱动的 26 个线程 / 20 MiB DLL**：不是我们的代码，只能靠不用 D3D。
* **图像解码保留 12 MiB 上限**：本轮实测只用到 0.37 MiB，不动。

## 5. 最终数字与目标——历史：nanoui 0.8.0，0.9.1 后不再适用

> 当前数字（0.9.1，2026-11-01）见 §8；下表是 0.8.0 的记录，保留作退步参照。
> 注意：0.9.1 的 release 隐藏窗口是 41.1–43.4 MiB、debug 是 45.4–47.7 MiB，
> 而可见窗口的滚动形态是 49.15–49.16 MiB——"余量只剩 2.3 MiB"是 **debug** 的口径。

release、2000 条、100 张缩略图、空闲 10 秒：

| 形态 | WS | 不含 L2（宪章口径） | 结论 |
| --- | ---: | ---: | --- |
| **默认（GDI 上屏，隔离开）** | **42.63** | **39.11** | **PASS（≤ 50），余量 7.4 MiB** |
| 同上，关掉探针自带诊断 | 42.59 | 39.07 | 一样（稳定态诊断不额外占） |
| 隔离关（对照） | 50.60 | 47.08 | 刚过 50；隔离本身值 8.0 MiB |
| `--d3d`（旧上屏） | 72.63 | 69.11 | FAIL，差在 D3D 的 30.0 MiB |
| 优化前（debug，同一探针口径） | 128.64 | 125.12 | FAIL |

> 分布：隔离开连续 6 次 42.58–42.63，隔离关 50.50–50.68。刚构建完的第一轮读到过
> 45.61（exe 代码页 3.01 vs 1.18），那是系统读新 exe 的瞬态，上界记在这里。

「不可压缩的下限」分解（默认形态，42.63 MiB）：

| 组成 | MiB | 能不能压 |
| --- | ---: | --- |
| Windows DLL 代码页（42 个模块，除 exe） | 16.5 | 不能（user32/dwrite/COM/输入栈） |
| `otto-lite.exe` 代码页 | 1.2 | 发布版的样子（探针诊断也在这 1.2 里） |
| 我们自己的私人页 | 23.5 | 见下 |
| └ 2000 条库 | 4.8 | 压得动但没必要（宪章要 2000 条可用） |
| └ L2 缩略图（宪章不计） | 3.5 | 预算可调小 |
| └ 画布 + 两张图集 + 解码保留 | 3.6 | 已是最小（512² / 512² / 1 MiB） |
| └ 启动堆 + 视图/上下文 + 线程栈提交 | ~11.0 | 唯一还没逐项拆开的账；要压得先做分配器剖析 |
| 映射文件（字体） | 1.3 | 已是按需 |

**结论：宪章的数字在真实窗口形态下达到了**（42.63 MiB，不含 L2 39.11，余量 7.4 MiB）。
要进一步压到 40 以下，只能动那 ~11 MiB 的堆/分配器，或者把 L2 预算调小
（宪章不计，但用户看任务管理器时算）。

## 6. 回归

```

**画面没变**：用 `--nanoui-snapshot` 对同一份 2000 行真图库各出一张 760×1400 PNG，
HEAD 与改动后**逐像素相同（0/1,064,000 个像素不同）**——缩略图、中文、预览条、
选中态都对得上。GDI 上屏的数据通路另有一项自检：把同一份画布用同一个
`BITMAPINFOHEADER` 走一次 `SetDIBitsToDevice` 画进 DIB，再逐字节比 ——
`lines=700 bytes=260/260`（采样 260 个字节点全等）。窗口 DC 回读在 DWM 下读不到内容
（GDI 与 D3D 都是 0/6），所以没有拿它当证据。

## 7. 建议

1. **默认 GDI 上屏**（本轮已改）：42.6 MiB、present p50 0.05 ms（D3D 4.17 ms）。
   若哪天要 vsync/GPU 合成，`--d3d` 一条命令切回，内存预算按 73 MiB 算。
2. **宪章 50 MiB 建议写成「真实窗口形态、不含 L2、进程 WorkingSet」**，并注明用
   `zig/mem.ps1 -Release` 取数；本轮 42.6 MiB（不含 L2 39.1）达标。
3. **隔离去不得**：它值 8 MiB（Shell/COM 栈不进我们进程），还是崩溃隔离的边界。
4. 想再往下压：先给那 ~11 MiB 的堆/视图账做一次分配器剖析（`std.heap` 快照 +
   分配点分类），再决定要不要给 L2 预算设上限（8–16 MiB）。

### 9.3 省掉的 6.14 MiB 是哪一块

**不是应用的功能，是探针自己。** `bench_scroll.zig` 以前为了拿「滚动经过的行 →
样本」的映射，在测内存之前又 `loadWith` 了一次同一份库（含 429 KB JSON 文本、
JSON 树、样本数组）。那份库只用来读 `samples.len` 和 `thumbs.has(sample)`，而
视图里本来就有同一份 `State.samples`。改成把 `state.samples` 传进去之后：

* 少一份 2000 行的库（arena 5.15 + 读缓冲/分配器余量 0.99 = 6.14）；
* 预取统计不变（`ready_arriving=346/346`、`ready_end=346`），没有任何功能被拿掉；
* 探针量的从此是**应用**，不是「应用 + 探针自己的副本」。

所以这条的数字要这么读：可见滚动形态的**应用**基线是 42.5，不是 48.8；
48.8 里有 6.1 是尺子自己的重量。§8 里「只剩 0.84 MiB」的结论因此偏悲观了 6 MiB。

### 9.4 预算：默认 64+16=80 改成 32+16=48，并夹住

改之前：`settings_store` 的 L2 默认 **64**，预览按 L2/4 派生 16，合计 **80**，
而设置面板的上限是 1024（预览能到 256）。宪章的「缩略图 + 预览 ≤ 48」一行代码
都没检查。现在：

* `app/src/mem_budget.zig` 是唯一政策：L2 ≤ 32、预览 = L2/2 夹在 4–16、合计 48；
* `settings_store` 读盘时把 64/128/999999 一律夹到 32；设置面板输入超限会**夹取
  并打印提示**，文本框回写生效值；
* `Thumbs.init` 打印 `otto-lite: cache budget l2=..MiB preview=..MiB`，这就是
  `membudget.ps1` 断言的输入（不是脚本自己猜的数）。

### 9.5 判据与反向证明

* `zig/membudget.ps1`：gdi 可见滚动 300 帧 **ws ≤ 50** 且 **l2+preview ≤ 48**，
  超了 exit 1；同时打印 `ws`、`ws-no-L2`、`budget`、`bytes/row` 与 5 万行投影。
* `health.ps1` 的「内存」行改为跑它：`[PASS] 42.50 MiB（目标 50） 预算 l2 32 +
  preview 16 = 48 MiB（上限 48）`。
* 反向证明（同一脚本）：
  * `-L2MiB 128` → `budget 128 + 16 = 144 > 48`，**红**；
  * `-L2MiB 128 -DistinctFiles -Rows 1200 -Frames 900` → 缓存真的填满
    （L2 18.22、kept 4.39），`ws=71.63 > 50`，**红**；
  * 改回默认 → `ws=42.53`、`budget 32+16=48`，**绿**。
* 浏览模式 90 MiB：`browse_page_test.zig` 新增两条——10 万行在 90 处拒绝、
  每行固定字节 +512 B 就越线；等于把「5 万行 × 你加的字节」变成可执行乘数。

### 9.6 一个必须说清楚的边界：库里有上千张**不同**图时

上面的 42.5 / 48.8 都是「2000 行共享 100 个文件」，L2 只装 1.56。把同一形态换成
1200 张不同图（`-DistinctFiles -Rows 1200 -Frames 900`）：

| 配置 | ws | L2 | kept | ws-no-L2 |
| --- | ---: | ---: | ---: | ---: |
| 默认 32+16 | **68.65** | 18.22 | 4.39 | 50.43 |
| 覆盖 128 | 71.63 | 18.22 | 4.39 | 53.41 |

也就是说：**总 ws ≤ 50 这条只在「可见行数 × 缩略图」不把缓存填满时成立**。
宪章表格自己写的口径是「常驻内存（不含 L2）≤ 50」，按那个口径默认配置是
50.43——**也越线 0.43**（再把图像图集/kept 算进「L2 图像账」是 46.06）。这不是
本轮能靠「省」解决的：要么承认 50 MiB 是「不含 L2」口径（宪章原文）并把图像
图集/kept 也算进 L2 账，要么把默认预算压到 ~2 MiB——那是拿回滚时的重新取图
延迟换内存，本轮明确不允许。
`membudget.ps1` 因此把 `ws-no-L2` 一起打印，避免下一个读报告的人被总 ws 误导。
