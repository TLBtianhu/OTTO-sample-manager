# 项目宪章

> **一个 Windows 原生的媒体素材管理器：用分级缓存把「找素材 → 预览 → 拖进宿主」的
> 每一步压到可见阈值以下；界面由 nanoui 承载并随需求向上游生长。**

这份文件定义"我们做的是什么、不做什么、怎么算做到了"。任何偏离它的改动，应该在
PR 里说明理由，而不是顺手做掉。

---

## 一、对"任何媒体一视同仁"的准确含义

一视同仁的是**交互契约**，不是**解码能力**：

```
任何媒体类型 → 同一条链路：索引 → 搜索 → 预览 → 拖出
```

不同的只是每个类型背后的 **provider**。这是刻意的分工，因为视频解码和音频解码
不是一个数量级的工程。

| 类型 | 例子 | 预览 provider | 缓存内容 |
| --- | --- | --- | --- |
| 音频 | wav / mp3 / flac | 自绘波形 + PCM 解码 | PCM、波形峰值 |
| 视频 | mp4 / mov / mkv | Windows Shell 缩略图 → 后续 Media Foundation 抽帧 | 缩略图、关键帧 |
| 图像 | png / jpg / psd / ai | Windows Shell 缩略图 | 缩略图位图 |
| 三维 | blend / fbx | Windows Shell 缩略图（装了 Blender 就有） | 缩略图位图 |
| 其它 | 任意有 shell handler 的文件 | Windows Shell 缩略图 | 缩略图位图 |

**关键决定：通用预览走 Windows Shell 的缩略图 API（`IShellItemImageFactory`），
不走 FFmpeg。**

理由有三条，每条都指向宪章本身：

1. **零转义**：那是 Explorer 自己用的同一个接口，一次调用直达系统；
2. **覆盖面**：装了 PS/AI/Blender/剪映，系统里就有对应 handler，我们不用为每种
   格式写一遍；
3. **体积**：FFmpeg 链接进来就是二三十 MiB，直接撞碎 5 MiB 的安装包目标。

视频的"拖动预览/逐帧"是另一件事，留到第二阶段，用 Media Foundation 的
`IMFSourceReader` 抽帧——同样是系统 API，同样不引入第三方运行时。

## 二、三根支柱

### 1. 分级缓存：比资源管理器更懂"哪些东西值得常驻"

资源管理器的模型是「每次打开 = 每次重新读」。我们的模型是「读一次，之后按热度
分层持有」。层级按单位成本排，不按感觉排：

| 级别 | 内容 | 单条成本 | 何时产生 | 驻留策略 |
| --- | --- | --- | --- | --- |
| **L0** | 目录项：路径、大小、mtime | ~0.05 ms | 导入扫描 | 全量，索引 |
| **L1** | 头信息：时长/采样率/声道、尺寸、编码 | 1–5 ms | 导入后台 | 全量，元数据库 |
| **L2** | 按类型：PCM+波形 / 缩略图位图 / 视频帧 | 音频 20–50 ms，缩略图 5–20 ms | 首次预览 / 预热 | 有界 LRU + 热度保护 |
| **L3** | 落盘：波形峰值、缩略图 | 一次 | L2 之后 | 磁盘，跨启动 |

规则：

- **L0/L1 永远全量**——便宜到可以忽略，却决定了列表能不能"一眼可读"；
- **L2 永远有界**——默认 256 MiB，可调到 1 GiB，绝不允许无上限；
- **L3 是跨启动的部分**，也是"比 Explorer 好"最持久的一条；
- **淘汰按热度，不按插入顺序**——环形队列会误伤反复使用的那几个素材。

### 2. 金属层：调用链上没有外来运行时

"零转义"不是"不抽象"，而是**一次调用直达系统**：

- ✅ Zig 里手写 `extern` 直接对应 DLL 导出（`ole32!DoDragDrop`、`shell32!SHCreateItemFromParsingName`）；
- ✅ 允许 Zig 自己的抽象（模块、泛型、arena）；
- ❌ WebView / JS 运行时出现在 UI 路径；
- ❌ C shim（`.c` / `.m` / `.java`）；
- ❌ 为系统能力再起代理进程，除非该能力本身要求跨位数。

这条规则解释了拖拽 helper 的存在：Melodyne 3.2.2 只接受 x86 源，那是**协议要求**，
不是偷懒。

### 3. nanoui 扩展版：一个 UI 树，而不是一层壳

- 声明式视图 + 虚拟列表 + 自绘文字，全部在 Zig 里；
- 平台能力通过**同一份 `Options` / API** 暴露（无边框、透明度、IME、拖拽）；
- 缺什么补什么，补完提回上游——**fork 里不写 app-specific 的补丁**。

判断标准：任何一处改动，问"一个做音乐播放器的陌生人会需要吗"。不需要，就留在 app 侧。

## 三、非目标

- **不做编辑器**：不剪视频、不做时间拉伸、不合成；
- **不做播放器**：预览是手段，不是产品；视频播放能力以"够判断素材"为限；
- **不做通用文件管理器**：只服务"素材 → 宿主"这一条路径；
- **不做跨平台优先**：Windows 是唯一一等公民，其它平台保持能编译即可；
- **不引入 FFmpeg / GStreamer 这类重型第三方运行时**（见"一视同仁"一节的理由）；
- **不做插件生态**：至少现在不做。

## 四、可度量目标

| 指标 | 目标 |
| --- | --- |
| 冷启动（2000 素材库） | ≤ 100 ms |
| 常驻内存（不含 L2） | ≤ 50 MiB |
| 列表滚动 380×700 | 60 fps |
| 音频首次试听（冷） | p95 ≤ 50 ms |
| 缩略图首次出现（冷） | p95 ≤ 80 ms |
| 重复预览（热） | ≤ 5 ms |
| 拖出到 Melodyne 3.2.2 | 100% 成功，无 Bug Reporter |
| 拖出多文件（200 个） | 一次拖出，宿主正常接收 |
| 安装包 | ≤ 5 MiB |

## 五、与资源管理器的差异

"更好用"必须落在具体能力上，否则是口号：

| 能力 | 资源管理器 | 本项目 |
| --- | --- | --- |
| 元数据 | 每次打开重新读 | 索引，启动即可查询 |
| 缩略图 | 有，但只在文件夹里看 | 跨目录索引 + 常驻缓存 |
| 波形 | 无 | 音频专用，跨启动 |
| 跨目录搜索 | 慢 | 索引 + 拼音/首字母 |
| 试听 / 粗剪预览 | 外部播放器 | 内联，毫秒级 |
| 拖出到宿主 | 系统默认 | 协议级实现 + 自动副本 |
| 分组 / 标签 | 无 | 一等公民 |
| 中文输入 | 系统默认 | 自己实现的 IME 路径 |
| 工作流预设 | 无 | 按宿主（AE/PR/剪映/Blender/Melodyne）区分拖出策略 |
