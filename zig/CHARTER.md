# 项目宪章

> **一个 Windows 原生的媒体素材管理器：用分级缓存把「找素材 → 预览 → 拖进宿主」的
> 每一步压到可见阈值以下；界面由 nanoui 承载并随需求向上游生长。**

这份文件定义"我们做的是什么、不做什么、怎么算做到了"。任何偏离它的改动，应该在
PR 里说明理由，而不是顺手做掉。

---

## 一、对"任何媒体一视同仁"的准确含义

一视同仁的是**交互契约**，不是**解码能力**：

```
任何媒体类型 → 同一条链路：索引 → 搜索 → 预览 → 拖出
```

不同的只是每个类型背后的 **provider**。这是刻意的分工，因为视频解码和音频解码
不是一个数量级的工程。

| 类型 | 例子 | 预览 provider | 缓存内容 |
| --- | --- | --- | --- |
| 音频 | wav / mp3 / flac | 自绘波形 + PCM 解码 | PCM、波形峰值 |
| 视频 | mp4 / mov / mkv | Windows Shell 缩略图 → 后续 Media Foundation 抽帧 | 缩略图、关键帧 |
| 图像 | png / jpg / psd / ai | Windows Shell 缩略图 | 缩略图位图 |
| 三维 | blend / fbx | Windows Shell 缩略图（装了 Blender 就有） | 缩略图位图 |
| 其它 | 任意有 shell handler 的文件 | Windows Shell 缩略图 | 缩略图位图 |

**预览不是一大堆 if-else，而是一张注册表。** 试听、试看、视频抽帧、三维预览是同一层级的
provider，共用一套契约（`Outcome` 只有 image / audio / frames / text / none 五个分支）；
UI 不认识"音频"或"视频"，只认识这五个分支。新增一种媒体 = 新增一个 provider，视图零改动。

**缩略图是身份指纹，不是预览的缩放。** 判据是"能不能和别的文件区分开"，不是"像不像原图"——
信息密度约等于哈希值。所以图标级允许低精度重采样、允许粗到 32 个采样点、允许退化成占位；
预览级才要求保真。这条直接决定了实现：WAV 的图标用 32 个等距窗口、每窗两帧（<1 ms），
而 Media Foundation 的音频宁可声明自己不能做图标——打开容器加 seek 实测 47–78 ms，
比整段解码还贵，**一个 32px 的图标不值得**。

**注意"缩略图"的真实性质：它是一个插件生态，不是我们的解码器。**

- 能不能出图，取决于**这台机器上装了什么缩略图 handler**：PS 装 PSD/AI，codec pack
  装 MKV，Blender 注册 .blend。同一份代码在两台机器上覆盖率可以完全不同。
- 因此 API 必须区分三种状态：**有图 / 没有 handler / 出错**。"没有预览"是一个诚实的
  答案，不是失败；但把"没有 handler"和"读文件失败"合并成一种，就永远说不清。
- **handler 是第三方进程内 COM 组件**，会被加载进我们的地址空间，崩了、挂了都不是
  我们的 bug。所以调用方不该假设它永远同进程——将来换到 helper 进程里跑，签名不变。
- "没有 handler" 要能**负缓存**并带过期：用户随时可能装一个 codec pack，把结论变成
  假的。
- 反过来，如果某个格式真的很重要却没有 handler，**写一个 `IThumbnailProvider` 比写
  解码器便宜得多**，而且 Explorer 也会跟着受益。

### 可发现、可解码、可调度是三件事

借自 Cutrans 的三问分离：**可解码 ≠ 可发现 ≠ 可调度**。

- **可解码**：把 PSD 变成像素——不归我们，归 handler；
- **可发现**：这台机器**有没有** PSD 的 handler——归注册表，不归渲染；
- **可调度**：用户装完 Photoshop 之后，谁去作废"不能预览"这个结论。

现在的实现只做了中间那个的暴力版本（渲染一次试试），缺两头。正确的做法：

```
能力表 = 枚举 HKCR\.<ext>\ShellEx\{e357fccd-a995-4576-b01f-234630154e96} 的默认 CLSID
```

它**不需要加载任何第三方 DLL** 就能回答"能不能预览"，把"发现"从"试错"里解放出来；
再用 `RegNotifyChangeKeyValue` 监听 `ShellEx` 变化，解决"可调度"。

**推论**：将来若我们自己写 handler，它也只能住在边缘（独立 COM 组件），不能进 app——
否则我们就从"聚合机"变成了"会翻译的聚合机"，被格式数量绑死。

**关键决定（已修订）：常用格式自己解，Shell 只做专业格式的兜底。**

最初写的是"通用预览走 Shell 的 `IShellItemImageFactory`"，理由是零转义、覆盖面和体积。
那三条仍然成立，但它把**所有**格式的预览权交给了一个我们既不写也审不了的第三方 handler：
handler 没装就没有预览，装坏了就是我们的进程崩。

现在每个 provider 自给自足、地位平等：

| 格式 | provider | 依赖 |
| --- | --- | --- |
| wav | `wasapi-pcm`（自己解码 + WASAPI） | 无 |
| flac | `native-audio`（vendor 的 zig-audio，纯 Zig 解码） | 无 |
| mp3 | `native-audio`（vendor 的 zig-audio，纯 Zig 解码）；`mf-audio` 兜底 | 无 |
| aac/m4a/wma | `mf-audio`（Media Foundation 解码） | 系统 codec |
| png/jpg/bmp/gif/tif | `image-wic`（WIC 解码） | 系统 codec |
| mp4/mov/wmv | `mf-video`（MF 抽首帧） | 系统 codec |
| psd/ai/blend 等 | `shell-thumbnail`（`IShellItemImageFactory`） | **第三方 handler** |

前五种是"我们自己能回答的"，不需要能力表、不看注册表；最后一种才是"问系统"。
**没有系统级快速通道**：Shell 只是表里的一项，排在后面，因为它是唯一需要别人装东西的。

体积目标没变（这些全是系统 API，没有一个第三方运行时）；零转义也没变（我们直呼 DLL）。

## 二、三根支柱

### 1. 分级缓存：比资源管理器更懂"哪些东西值得常驻"

资源管理器的模型是「每次打开 = 每次重新读」。我们的模型是「读一次，之后按热度
分层持有」。层级按单位成本排，不按感觉排：

| 级别 | 内容 | 单条成本 | 何时产生 | 驻留策略 |
| --- | --- | --- | --- | --- |
| **L0** | 目录项：路径、大小、mtime | ~0.05 ms | 导入扫描 | 全量，索引 |
| **L1** | 头信息：时长/采样率/声道、尺寸、编码 | 1–5 ms | 导入后台 | 全量，元数据库 |
| **L2** | 按类型：PCM+波形 / 缩略图位图 / 视频帧 | 音频 20–50 ms，缩略图 5–20 ms | 首次预览 / 预热 | 有界 LRU + 热度保护 |
| **L3** | 落盘：波形峰值、缩略图 | 一次 | L2 之后 | 磁盘，跨启动 |

规则：

- **L0/L1 永远全量**——便宜到可以忽略，却决定了列表能不能"一眼可读"；
- **L2 永远有界**——默认 256 MiB，可调到 1 GiB，绝不允许无上限；
- **L3 是跨启动的部分**，也是"比 Explorer 好"最持久的一条；
- **淘汰按热度，不按插入顺序**——环形队列会误伤反复使用的那几个素材。

#### 一个缓存层，不是四个

L2 的**载荷**按类型不同（PCM / 波形 / 缩略图位图 / 视频帧），但**机制只有一套**：

```
Cache: key → { payload: []u8, cost_bytes, last_used, hits, protected }
         一个预算  一套 LRU  一份统计  同一个淘汰器
```

调用方不关心"这是音频缓存还是缩略图缓存"，只问 `get(key)` / `put(key, bytes)`。
这样预算、命中率、淘汰策略、监控面板都只有一份实现，新增媒体类型**不需要新增缓存**。

唯一的例外是**公平性**：视频缩略图一次能刷进来几百张，会把 PCM 挤掉。所以淘汰器
要支持**按载荷类的软配额**（例如 PCM 至少保留 40% 预算，缩略图不超过 50%），
这不是四套缓存，是同一个缓存上的准入权重。

### 2. 金属层：调用链上没有外来运行时

"零转义"不是"不抽象"，而是**一次调用直达系统**：

- ✅ Zig 里手写 `extern` 直接对应 DLL 导出（`ole32!DoDragDrop`、`shell32!SHCreateItemFromParsingName`）；
- ✅ 允许 Zig 自己的抽象（模块、泛型、arena）；
- ❌ WebView / JS 运行时出现在 UI 路径；
- ❌ C shim（`.c` / `.m` / `.java`）；
- ❌ 为系统能力再起代理进程，除非该能力本身要求跨位数。

这条规则解释了拖拽 helper 的存在：Melodyne 3.2.2 只接受 x86 源，那是**协议要求**，
不是偷懒。

### 3. nanoui 扩展版：一个 UI 树，而不是一层壳

- 声明式视图 + 虚拟列表 + 自绘文字，全部在 Zig 里；
- 平台能力通过**同一份 `Options` / API** 暴露（无边框、透明度、IME、拖拽）；
- 缺什么补什么，补完提回上游——**fork 里不写 app-specific 的补丁**。

判断标准：任何一处改动，问"一个做音乐播放器的陌生人会需要吗"。不需要，就留在 app 侧。

## 三、非目标

- **不做编辑器**：不剪视频、不做时间拉伸、不合成；
- **不做播放器**：预览是手段，不是产品；视频播放能力以"够判断素材"为限；
- **不做通用文件管理器**：只服务"素材 → 宿主"这一条路径；
- **不做跨平台优先**：Windows 是唯一一等公民，其它平台保持能编译即可；
- **不引入 FFmpeg / GStreamer 这类重型第三方运行时**（见"一视同仁"一节的理由）；
- **不做插件生态**：至少现在不做。

## 四、可度量目标

| 指标 | 目标 | 怎么量 |
| --- | --- | --- |
| 冷启动（2000 素材库） | ≤ 100 ms | `--bench`：CreateProcess → 首帧报告行；**便携/安装形态**（有字体索引缓存），dev 首次无缓存约 130 ms（dev 缓存现在也落在 `%LOCALAPPDATA%\OTTO\dev`） |
| 常驻内存（不含 L2） | ≤ 50 MiB | `mem.ps1`：**真实窗口**空闲 10 s 的 WorkingSet，减 L2 图像账 |
| 列表滚动 380×700 | 60 fps | `--bench-scroll`：真实窗口、屏外、`WS_EX_NOACTIVATE`，每 16 ms 注入滚轮 300 帧 |
| 音频首次试听（冷） | p95 ≤ 50 ms | `--bench` 的 `play()` → `position>0` ×20 |
| 缩略图首次出现（冷） | p95 ≤ 80 ms | `--bench` 的冷 100 张 |
| 重复预览（热） | ≤ 5 ms | L2/L3 命中 |
| 拖出到 Melodyne 3.2.2 | 100% 成功，无 Bug Reporter | **人工**（无自动化替代） |
| 拖出多文件（200 个） | 一次拖出，宿主正常接收 | **人工** |
| 安装包 | ≤ 5 MiB | `package.ps1` 产物 |

"怎么量"这一列不是装饰：**同一个目标换个口径能差一倍**（headless 首帧比真实窗口低，L2 算不算内存差 3.5 MiB）。
数字必须和口径一起引用，否则它只是宣传。

当前实测（0.2.x，见 `PERF.md` 与 `MEMORY.md`）：首帧 117–126 ms（便携热 100）、内存 42.6 MiB、滚动 62.5 fps、
音频 p95 19 ms、缩略图冷 p95 20 ms、安装包 1.58 MiB。**只有前两项需要按上面的口径解读。**

## 五、竞争面只有一个：Windows 资源管理器

不是 Eagle，不是 Billfish，也不是剪映自带的素材库。那些产品的前提是**你把素材导入
到它们的库里**；我们不导入。我们和 Explorer 面对的是**同一批文件、同一个目录、同一个
"双击打开"的时刻**。

这决定了三条不可让的原则：

1. **不导入**——索引就地建立，素材留在原目录；卸载后目录原样还在；
2. **不搬运**——不建影子库、不复制、不改目录结构（自动副本除外，那是拖出策略）；
3. **不接管**——用户随时可以用 Explorer 打开同一个文件夹，两边看到的是同一份文件。

### 我们比 Explorer 强在哪

Explorer 真正缺的不是功能，是**记忆**：每打开一个文件夹，它都是冷启动。

| 能力 | 资源管理器 | 本项目 |
| --- | --- | --- |
| 元数据 | 每次打开重新读 | 索引，启动即可查询 |
| 缩略图 | 有，但只在当前文件夹 | 跨目录索引 + 常驻缓存 |
| 波形 | 无 | 音频专用，跨启动 |
| 跨目录搜索 | 慢，且按文件名 | 索引 + 拼音/首字母 + 元数据 |
| 预览延迟 | 每次现场解码 | 冷启动一次，之后常驻 |
| 拖出到宿主 | 系统默认 | 协议级实现 + 自动副本 |
| 分组 / 标签 | 无 | 一等公民 |
| 中文输入 | 系统默认 | 自己实现的 IME 路径 |
| 工作流预设 | 无 | 按宿主（AE/PR/剪映/Blender/Melodyne）区分拖出策略 |
| 最近用过什么 | 无 | 热度表驱动预热与排序 |

### 我们不跟 Explorer 争的

- **文件操作**：重命名/删除/移动/权限，交给系统，我们最多转发；
- **格式覆盖**：Explorer 能预览的，我们调同一个 Shell API，本来就不该输；
- **系统集成**：文件关联、属性页、右键 shell 菜单，沿用系统的。

### 但手感必须对齐

用户不会为了"多一点功能"换掉 Explorer，却会因为"快捷键不对"放弃。所以：

- 快捷键照抄（F2 重命名、Delete、Ctrl+C/V、F5 刷新、Backspace 返回）；
- 右键菜单语义对齐（在资源管理器中显示、复制路径、属性）；
- 拖拽行为对齐（多文件、拖拽缩略图、修饰键语义）。

**Explorer 的手感 + 记忆 + 工作流策略**——这三样加起来才是"更好用"。

## 六、与 Cutrans 的关系

Cutrans（同一作者的媒体工作站，Zig 重写中）是更大的目标；本项目是它**从另一端长出来的
一个垂直切片**——Cutrans 的宪法里写着「只加载素材表 = 素材暂存管理器」，本项目就是那句话
的可运行实例。

所以判断一个改动做得好不好，除了宪章本身，还有第二个问题：

> **这条能不能原样放进 Cutrans？**

### 四条边界（保证回灌时不用重写）

1. **`zig/core` 不碰平台**——它只认路径、字节、JSON；Win32 一律在外面。
2. **缓存是纯函数**——键由内容/元数据决定，删光缓存不丢任何用户数据。
3. **用户数据是真源**——分组、标签、收藏不随索引重建而消失。
4. **口岸只碰系统**——监听、缩略图、拖拽、窗口，全部是可替换的外围。

### 回灌清单（本项目 → Cutrans）

| 产出 | 在 Cutrans 里对应 |
| --- | --- |
| `zig/core` 的素材表与重建规则 | 素材表（源宪法：名↔地址↔指针） |
| 统一缓存层（预算 / LRU / 软配额 / 统计） | L2/L3 的记账器与驱逐器 |
| Shell 缩略图、文件监听、拖拽、剪贴板 | `source/` 与 `ui/` 的 Windows 口岸 |
| nanoui 的窗口 / IME / 字体补丁 | `ui/` 的上游依赖 |
| 热度的持久化与预热调度 | 时机三轨（点播 / 预判窗 / 闲时）的雏形 |

### 反向输入（Cutrans → 本项目）

- **帧化与 `t` 轴**：本项目的试听曲线就是一条极简时间轴，将来可以直接换成帧语义；
- **播放头门禁**（`allowed = has`）：没物化就不显示、不假装，已写进本宪章；
- **口岸三件套**（探测 / 协商 / 监听变化）：缩略图与设备能力的接入方式。

### 明确不做的

不把 Cutrans 的插件体系、流协议、帧调度搬进来。本项目只需要它的**存储经济学与口岸法**，
不需要它的**时间机器**。

## 七、身份与注释：路径是地址，不是身份

这一节来自对 Cutrans 宪法的吸收，也解决我们自己的一个真问题。

### 问题

如果我们用路径当身份：

- 文件一改名，分组/标签全变成孤儿；
- 用户把文件夹挪个位置，一篇"红标"；
- 索引重建一次，注释就可能对不上。

反过来，如果我们自己给每个文件铸一个 id 并存在库里，那么**注释就住进了一个可重建的
数据库**——按 Cutrans 的说法，这叫"缓存偷偷升格成跨时间 ABI"（L1351），是最危险的一类
错误：删缓存等于删用户数据。

### 解法：让操作系统发号

Windows 已经给了稳定身份：

- `GetFileInformationByHandle` → `dwVolumeSerialNumber` + `nFileIndexHigh/Low`
  （NTFS 上跨改名、跨同卷移动保持不变）；
- `OpenFileById` → 由身份反解出路径。

于是三层各归其位，和 Cutrans 的"身份 / 地址 / 名字"完全同构：

| 层 | 本项目 | 来源 |
| --- | --- | --- |
| 身份 | 卷序列号 + File ID | OS 发，我们不铸 |
| 地址 | 路径 | 可从身份重建（`OpenFileById`） |
| 名字 | 显示名 | 可从地址推导 |

**用户注释（分组、标签、收藏、评分）键在身份上，不在路径上。** 改名不丢、同卷移动不丢、
索引重建也不丢——因为注释住的不是索引，是它自己的表。

### 边界与回退

- File ID 的稳定性只在 NTFS/ReFS 上有保证；FAT32、exFAT、部分网络共享退化；
- 退化时回退到 `路径 + 大小 + mtime`，并在 UI 上标明"此素材的身份不稳定"；
- 注释表本身也要能导出/导入（用户换机器、换卷时不是死路）。

## 八、零转义的边界

"零转义"只在**我们自己的调用链**上成立：

- 内部：Zig 直呼 DLL 导出，没有 C shim、没有 WebView、没有代理进程；
- **对外部 Shell 面，转义是必然的**：`CF_HDROP` 只认路径、缩略图只认 PIDL、
  拖拽只认 HWND 与 COM 接口——这些 ABI 里没有塞 u64 的缝。

承认这一点，并把它锁死：**所有对外的身份↔地址翻译，只允许出现在 `zig/ports/` 里**
（或 app 侧等价的一个模块），核心代码不许出现路径拼接、PIDL、HWND。

这不是对"零转义"的妥协，而是给它划清边界：**核心零转义，口岸必须转义，且只准在口岸。**

### 第二个进程：缩略图隔离（M4）

"不引入代理进程"约束的是**我们自己的调用链**；缩略图 handler 不是我们的代码。
`IShellItemImageFactory::GetImage` 会把第三方注册的**进程内 COM 组件**（PS / AI /
Blender、各种 codec pack 的 DLL）加载进调用方进程——它越界、死循环、弹框，都不是
OTTO 能防的。M4 起这条调用整体搬进 `otto-thumb-host.exe`：

- 同一份构建的第二个 exe（`zig build` 一次出两个），不是脚本、不是外部工具；
- 边界上只有字节：`u32 path_len | path` → `status | 宽/高/跨度/字节数 | BGRA`，
  没有 COM 指针、没有 HWND / PIDL 跨过来（与本节"只准在口岸"同一条约束）；
- OTTO 自己崩了，`KILL_ON_JOB_CLOSE` 的 Job 会把 helper 一起收掉——不留孤儿进程。

这是"生态逼的"例外，和拖拽必须经过 OLE 同类：不是把转义挪进核心，而是把不可信的
第三方关进另一个**可牺牲**的进程。

## 九、三种形态：开发产物、便携版、安装版

**编译产物不是分发物。** `zig-out/bin/otto-lite.exe` 是开发环境里的东西：没有版本号、
可能是 debug 构建、可能依赖旁边的工作树。它的唯一用途是**再生成便携版与安装包**，
本身不该被用户使用，也不承载任何运行数据。同一台电脑上，开发时是程序员、日常使用时
是用户：程序员跑 `zig build`，用户装安装包，两者用的不是同一个运行环境。

| 形态 | 谁用 | 程序在哪 | 数据在哪 |
| --- | --- | --- | --- |
| **编译产物** | 只有 CI / 开发者，用来产出分发物 | `zig-out/` | **无（必须纯净）**；dev 运行数据在开发者的 `%LOCALAPPDATA%\OTTO\dev`，不属于产物 |
| **便携版** | 用户拷走，自包含 | 任意目录 | `<exe 目录>\data` |
| **安装版** | 用户日常使用 | 安装目录（默认 `%ProgramFiles%\OTTO Lite`） | `%APPDATA%\OTTO` |

规则：

1. **判据是标记，不是路径猜测。** 便携版可能被解压到任何地方，不能靠"路径里有没有
   Program Files"来认；安装版也不该假设自己一定装在 C 盘。
2. **安装目录永不写数据。** `Program Files` 需要提权，写在那里等于把自己变成管理员
   程序；数据一律进 `%APPDATA%`（多用户各自一份）或 `%PROGRAMDATA%`（共享库，
   要单独决定）。
3. **编译产物必须纯净。** `zig-out/bin` 只允许出现构建产出的 exe / pdb；dev 的设置、
   库、缓存、更新包都在 `%LOCALAPPDATA%\OTTO\dev`（没有 `LOCALAPPDATA` 时退回
   `%TEMP%\OTTO-dev`）。dev 形态同样**绝不碰真实 `%APPDATA%\OTTO`**，否则"测用户
   状态"这件事本身就失真了。从 `zig-out` 拷一份 exe 出去也必须是干净的。
4. **分发物由打包步骤生成**：版本号、标记文件、README、图标都由脚本产出，不靠人手工
   从 `zig-out` 里拷一个 exe 出来。

这跟 Cutrans 的"双态发号"是同一个思路：**运行环境不同，行为就该不同，而且这个不同
必须是显式判定的，不是碰巧的。**

## 十、0.x 的规矩：不做兼容，只做当前最优

1.0.0 之前，这个软件**仍然处在"第一次做"的状态**：

- 数据格式、命令行、模块边界都可以随时推翻，目标是**拓扑意义上的最优解**，不是增量修补；
- 任何"为了兼容"的代码必须能回答"谁在用"；答不出来就删掉；
- 已经写下的旧数据迁移（对 Electron 格式的 `reconcile`）是给**现存用户**的，不是给未来的自己——
  保留它是选择，不是义务；
- **更新检查仍然要设计**：检查 → 下载 → 验签 → 替换这条链路是软件的基本能力，跟"现在还没有
  真正的更新包"不矛盾。先把接口与假 feed 的测试做出来，真 feed 与签名发布等有用户再说。

判据很简单：**为一个还不存在的人写的代码，是在给自己加税。**

### 上游不是依赖

上游不回也不阻塞：**fork 即真源**。`TLBtianhu/nanoui` 就是我们要长期维护的那一支，
上游合并是加分项，不是前置条件。由此推出两条纪律：

- 补丁在 fork 上必须自洽、可独立构建，不假设上游会收；
- 仍然保持"通用能力"的写法（不写 app-specific），因为通用补丁在 fork 里也更好维护，
  而且万一上游收了，我们就是零成本。
